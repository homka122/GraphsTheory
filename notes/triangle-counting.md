# Подсчёт треугольников (TC) в D-Galois

Код: `deps/Galois/lonestar/analytics/distributed/triangle-counting/tc.cpp`.
Нужен симметричный граф без петель и кратных рёбер, запуск с `-symmetricGraph`.

## 1. Ориентация рёбер

Без ориентации каждый треугольник находится 6 раз: из каждой вершины, в двух порядках.

Ребро оставляют только от вершины меньшей степени к большей, при равной степени — от меньшего номера к большему
(`deps/Galois/libcusp/include/galois/graphs/GenericPartitioners.h:52`, `keepEdge`):

```cpp
bool keepEdge(uint32_t src, uint32_t dst) const {
  if ((destDegree > sourceDegree) ||
      ((destDegree == sourceDegree) && (src < dst)))
    return true;
```

У каждого треугольника ровно одна вершина, из которой выходят обе стрелки. Только из неё он и считается:

```
      b
     ↗ ↘
    a → c        обе стрелки выходят из a → треугольник считается только из a
```

Почему от меньшей степени к большей: у хаба остаётся мало исходящих рёбер, и длинные списки не пересекаются.

## 2. Оператор (`tc.cpp:102`)

Вызывается для каждой мастер-вершины `v`: для `w ∈ out(v)`, для `x ∈ out(w)` проверяет `x ∈ out(v)`.
Если да — треугольник `v-w-x`.

```cpp
void operator()(GNode v) const {
  size_t numTriangles_local = 0;
  for (auto vIter : graph->edges(v)) {            // w ∈ out(v)
    GNode w = graph->getEdgeDst(vIter);
    ...
    for (auto wIter : graph->edges(w)) {          // x ∈ out(w)
      auto x = graph->getEdgeDst(wIter);
      Graph::edge_iterator vvIter = vIterBeg;     // ищем x в out(v) с начала
      while (graph->getEdgeDst(vvIter) < x && vvIter < vIterEnd)
        vvIter++;
      if (vvIter < vIterEnd && x == graph->getEdgeDst(vvIter))
        ++numTriangles_local;
    }
  }
  numTriangles += numTriangles_local;             // DGAccumulator
}
```

- Списки соседей заранее отсортированы (`tc.cpp:169`, `sortEdgesByDestination`), поэтому `x` ищется проходом,
  пока номер соседа меньше `x`.
- Счётчик сначала локальный, в общий `DGAccumulator` прибавляется один раз на вершину.
- Неэффективность: поиск (строка 111) каждый раз начинается с начала списка `v`, хотя `x` растёт.
  Шагов `deg(v) × deg(w)` вместо `deg(v) + deg(w)`.

Пример:

```
v → {2, 5, 7},  2 → {5, 9},  5 → {7},  7 → {}
w=2: x=5 ∈ out(v) → v-2-5 ✓;  x=9 нет
w=5: x=7 ∈ out(v) → v-5-7 ✓
итого 2
```

## 3. Разбиение (`deps/Galois/libcusp/include/galois/graphs/MiningPartitioner.h`)

**3а. Свои вершины** (строки 429–435). Мастера — непрерывные блоки номеров, у мастера его ориентированные
исходящие рёбра. Чужой конец ребра становится зеркалом:

```cpp
if (graphPartitioner->keepEdge(n, dst)) {
  if (graphPartitioner->retrieveMaster(dst) != myID)
    incomingMirrors.set(dst);                  // dst станет зеркалом у меня
```

**3б. Рёбра между зеркалами** (строки 593–602). Ребро `n → dst` уходит на процесс `h`, если на `h` есть и `n`, и `dst`:

```cpp
if (graphPartitioner->keepEdge(n, dst))
  for (unsigned h = 0; h < net.Num; h++)
    if (h != net.ID)
      if (proxiesOnOtherHosts[h].test(n))
        if (proxiesOnOtherHosts[h].test(dst))
          numOutgoingEdges[h][n - globalOffset] += 1;
```

```
процесс 0: мастер v, v → w (w у процесса 1), v → x (x у процесса 2)
процесс 1 видит у себя w → x, у процесса 0 есть и w, и x → шлёт w → x процессу 0
процесс 0: v → w, v → x, w → x  — треугольник считается локально
```

Лишнего не шлётся: если `x` не сосед `v`, его нет на процессе 0, и треугольника `v-w-x` нет.

### Это OEC?

За основу взят OEC, но рёбра дублируются. Шапка файла: «Graph mining partitioning that duplicates edges.
Currently only supports an outgoing edge cut.»

|                       | Обычный OEC (BFS, SSSP)      | MiningPartitioner (TC)                        |
|-----------------------|------------------------------|-----------------------------------------------|
| Мастера               | блоки номеров                | блоки номеров (как OEC)                       |
| Рёбра мастера         | все исходящие у мастера      | исходящие у мастера, только ориентированные   |
| Зеркала               | без рёбер                    | с рёбрами между собой                         |
| Одно ребро хранится   | ровно на одном процессе      | может быть на нескольких                      |

Разбиение не выбирается: TC всегда строит `MiningGraph<..., MiningPolicyDegrees>`
(`deps/Galois/lonestar/libdistbench/include/DistBench/MiningStart.h:132`), флаг `--partition` не действует.

## 4. Синхронизация

- Один `do_all` по мастерам (`tc.cpp:88`), раундов нет, Gluon sync не вызывается. Sync и Async не различаются.
- Вся связь во время подсчёта — `numTriangles.reduce()` (`tc.cpp:96`): одно число от каждого процесса, `MPI_Allreduce`.
- Весь обмен данными — при построении графа (рассылка рёбер зеркал). `Timer_N` его не включает,
  он виден в `GraphConstructTime`.
- Для масштабируемости: дублирование рёбер растёт с P (память, время построения); мастера раздаются блоками номеров,
  а не по работе, и `steal()` не переносит работу между процессами.

## 5. Масштабируемость: что ожидать и что мерить

```
время TC = построение графа  +  подсчёт  +  одно сложение
            (рассылка рёбер,     (без сети)    (~мкс)
             дублирование)
```

- Подсчёт — чистые вычисления без раундов и sync, масштабируется почти идеально при равной работе.
- Работа делится неравно: мастера раздаются блоками номеров, а работа вершины ≈ сумма `deg(v) × deg(w)` по соседям.
  На графе с хабами (LiveJournal) один блок может быть намного тяжелее. `steal()` между процессами работу не переносит.
- Построение графа с ростом P дорожает: рёбер между зеркалами больше, они дублируются.

Что мерить (P = 1…6):

| Что                              | Откуда |
|----------------------------------|--------|
| время подсчёта                   | `Timer_N` |
| время построения графа           | `GraphConstructTime` |
| работа по процессам              | `TC_N, Time` по процессам: один `do_all` на прогон, округление до мс не мешает |
| рёбра на процессе (дублирование) | статистику ещё предстоит найти |

Сборка: цель `triangle-counting-dist` входит в `galois-apps`, бинарник `build/bin/triangle-counting-dist`.
Нужен симметричный граф (`-symmetricGraph`): RGG и roadNet-PA подходят, LiveJournal ориентированный — его нужно симметризовать.

## 6. Результаты (19.10.2026, 20 прогонов, 1 поток на процесс, `results/tc-scaling-20/`)

Число треугольников совпадает с SNAP при любом P: LiveJournal 285 730 264, roadNet-PA 67 150.

roadNet-PA слишком мал: подсчёт идёт единицы мс, а таймер считает целыми мс.

- LiveJournal: 3.47× = 6 / (1.41 перекос × 1.21 рост суммарной работы). Перекос — от разбиения блоками номеров
  при хабах; рост суммарной работы на 21% — вероятно, общая память (не проверено).
- RGG: степени ровные, работа делится почти поровну (148–150 мс у всех 6 процессов), ускорение 5.6×.
- Построение графа почти не ускоряется: LiveJournal 5.3 → 4.2 с, rgg 2^21 1.26 → 0.41 с.

  Треугольников с каждым удвоением ×2.22 (средняя степень растёт как ln n), поэтому честнее время на треугольник
  на процесс: 20.6 → 20.9 → 21.8 нс, эффективность 0.94.
